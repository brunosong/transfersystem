# ADR 0005. [시스템] 청크 내용을 Kafka 메시지에 직접 싣고 크기를 제한한다

- 상태: 채택
- 날짜: 2026-11-04
- 관련 문서: [시스템 설계](../system/architecture.md#3-메시지-크기), [이벤트와 메시지](../domain/events.md), [ADR 0002](0002-target-agent.md)
- 관련 모듈: `message-contracts`, `transfer-messaging`, `infrastructure/docker-compose`

## 맥락

Kafka는 큰 데이터를 나르는 데 맞춰져 있지 않다. 기본 메시지 제한이 약 1MB이고, 메시지가 크면 브로커 메모리와 복제에 부담을 주며 같은 파티션의 뒤 메시지를 민다. 큰 데이터를 다룰 때는 내용을 저장소에 두고 위치만 보내는 **클레임 체크**가 흔히 쓰인다.

커리큘럼 문서도 메시지 하나로 보내기에는 크다. 그래서 이 시스템은 문서를 과목별 청크로 나눠 보낸다. 그런데 지금 설정은 제한을 약 15MB까지 올려 둔 상태라, 큰 메시지가 그대로 통과한다.

정할 것은 두 가지다. 내용을 Kafka에 직접 실을지, 싣는다면 큰 내용을 어떻게 다룰지다.

시드 데이터(과목 40개, 차시 20,000개)와 같은 구조로 크기를 쟀다. Avro 값은 인코딩 규칙으로 계산했다.

| 과목 하나의 모양 | Avro 크기 |
|---|---|
| 단원 5 × 차시 100, 설명 짧음 (시드) | 약 32KB |
| 단원 10 × 차시 200, 설명 짧음 | 약 132KB |
| 단원 5 × 차시 100, 차시 설명 500자 추가 | 약 765KB |
| 단원 5 × 차시 100, 차시 설명 2,000자 추가 | 약 3MB |

## 선택지

| | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | **과목별로 나눠 직접 싣고, 1MB로 제한한다** | 대상이 Kafka만 알면 된다. 레지스트리가 내용까지 검사한다. 시드 크기에는 충분하다 | 설명이 긴 콘텐츠는 제한에 걸릴 수 있다 |
| B | 클레임 체크: 내용은 저장소에 두고 위치만 싣는다 | 크기 제한이 사실상 없다 | 대상이 저장소 권한까지 가져야 한다. 장애 지점이 늘고, 레지스트리가 내용을 검사하지 못한다 |
| C | 지금처럼 제한을 15MB로 올려 둔다 | 고칠 것이 없다 | 큰 메시지의 부담을 그대로 진다. 문제가 생겨야 알게 된다 |
| D | Kafka 없이 API로 보낸다 | 가장 단순하다 | 대상이 죽어 있을 때 쌓아 둘 곳과 재시도를 직접 만들어야 한다. 대상마다 받는 API가 필요하다 |

## 결정

**A를 쓴다.** 크기 문제가 실제로 생기지 않았는데 B의 비용을 먼저 치르지 않는다.

B의 비용은 인프라만이 아니다. 대상이 저장소에 접근하려면 권한을 받아야 해서 [ADR 0002](0002-target-agent.md)의 "대상과의 약속은 계약 하나뿐"이 흐려지고, 서비스 팀에 요구할 것이 늘어난다.

제한에 걸리는 콘텐츠가 있을 수 있으므로 동작을 정해 둔다.

- **제한은 1MB다.** 생산자 `max.request.size`와 토픽 `max.message.bytes`를 맞춘다. 15MB 설정은 지운다.
- **접수할 때 검사한다.** 청크 내용 하나가 900KB를 넘으면 배포를 접수하지 않고(422), 어느 과목이 얼마나 큰지 알려 준다. 나머지 약 100KB는 봉투와 레코드 오버헤드를 위한 여유다.
- **압축은 `lz4`를 쓰지만 제한은 압축 전 크기로 판단한다.** 시드는 반복이 많아 압축률을 믿을 수 없다.

## 결과

### 얻은 것
- 대상은 Kafka와 계약만 알면 된다. 서비스 팀에 넘기기 쉽다.
- 내용까지 호환성 검사를 받는다.
- 큰 메시지가 조용히 지나가지 않는다. 일부만 나가고 실패하는 대신 시작 전에 막는다.

### 감수한 것
- **900KB를 넘는 과목은 배포할 수 없다.** 차시 설명이 500자만 길어져도 가까워진다. 그런 콘텐츠가 있으면 과목을 더 잘게 나누거나 B로 바꿔야 한다.
- **`SUBJECT` 하나를 한 청크로 보는 모델을 전제로 한다.** 단원 단위로 나누면 제한에서 멀어지지만, 반영과 재전송 단위가 바뀌므로 지금 하지 않는다.
- **크기 값 일부는 아직 계산값이다.** 실제 직렬화와 압축은 스키마를 만든 뒤 잰다.

## 실무에서는

이 결정의 크기 근거는 시드 데이터다. 실제 서비스의 콘텐츠 크기는 반영하지 못했다. 실제 크기를 알게 되면 이 결정이 맞는지 다시 본다.

## 바꾸려면

**B로 바꾸기**: `content`를 저장 위치 참조로 바꾼다. 내용은 이미 `deployment_chunk_payload`에 보관하므로, 그 표를 객체 저장소로 옮기고 대상에 권한을 주면 된다. 깨지는 계약 변경이므로 새 스키마와 새 토픽으로 낸다. 900KB 거절이 자주 일어나면 고려한다.

**제한 올리기**: 2MB 정도까지는 설정만 바꾸면 된다. 그 이상은 파티션을 미는 시간이 길어지므로 B를 먼저 검토한다.
