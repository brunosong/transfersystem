# ADR 0004. [시스템] 명령 발행에 별도 아웃박스 테이블을 쓴다

- 상태: 채택
- 날짜: 2026-11-04
- 관련 문서: [도메인 모델](../domain/model.md), [ADR 0003](0003-defer-saga.md)
- 관련 모듈: `deployment-service`의 `outbox`, `infrastructure/outbox`

## 맥락

청크 상태를 바꾸는 DB 트랜잭션과 Kafka 발행은 하나로 묶을 수 없다. 묶지 않으면 이런 일이 생긴다.

| 시점 | 중간에 죽으면 |
|---|---|
| 접수 후 뼈대 발행 | 뼈대가 나가지 않는다. 응답 기한이 지나 실패로 드러나고 재전송으로 복구된다 |
| 뼈대 반영 후 과목 발행 | 과목이 `WAITING`인 채로 멈춘다. 응답 기한은 `SENT`에만 걸려 있어 배포가 영원히 진행 중으로 남는다 |

그래서 "보낼 것을 상태 변경과 같은 트랜잭션에 기록하고, 따로 읽어서 발행하는" 구조가 필요하다. 정할 것은 그 기록을 어디에 두느냐다.

## 선택지

| | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | **별도 아웃박스 테이블** | 교과서 그대로의 패턴이라 직접 익히기 좋다. 메시지 종류가 늘어도 같은 경로로 보낸다. 지금 코드에 이미 있다 | 청크 상태와 발행 상태가 두 표로 나뉜다. 키별 순서를 직접 지켜야 한다 |
| B | 청크 표를 발행 기준으로 쓴다 (발행 시각 칸 추가) | 표와 스케줄러가 줄어든다. 청크 번호로 정렬하면 순서가 맞는다 | 청크 명령만 보낼 수 있다. 패턴의 변형이라 설명이 더 필요하다 |
| C | 트랜잭션 커밋 후 바로 발행한다 | 가장 단순하다 | 사이에 죽으면 과목이 멈춘다. 멈춘 청크를 찾아내는 장치를 결국 만들어야 한다 |

## 결정

**A를 쓴다.** 이 프로젝트는 Kafka와 메시징 패턴을 직접 써 보며 배우는 것도 목적이다. B가 표는 더 적지만, 지금 메시지 종류가 하나뿐일 때의 이점이고 패턴을 그대로 익히는 쪽을 택했다.

### 다만 지금 구현은 고친다

[메시지 순서](../domain/model.md#7-메시지-순서)를 지키려면 지금 코드로는 안 된다.

| 지금 | 문제 | 고칠 방향 |
|---|---|---|
| 기본 키가 UUID이고 조회에 정렬이 없다 | 생성 순서를 알 수 없다 | 증가하는 순번 `seq`를 두고 그 순서로 읽는다 |
| `kafkaTemplate.send`를 비동기로 보내고 다음 행으로 넘어간다 | 앞 행의 실패를 모른 채 뒤 행이 나가 순서가 뒤집힌다 | 행마다 브로커 응답을 확인하고 넘어간다. 실패하면 같은 키의 뒤 행은 이번 주기에 보내지 않는다 |
| 실패한 행을 `FAILED`로 적지만 스케줄러는 `STARTED`만 읽는다 | 일시적 오류로 실패한 행이 다시 나가지 않는 것으로 보인다 | 일시적 실패는 상태를 그대로 두어 다음 주기에 다시 보낸다. `FAILED`는 다시 보내도 소용없는 행에만 쓴다 |
| 청크 키가 `UUID.randomUUID()`다 | 순서 보장 단위가 없다 | 행에 키(대상 + 커리큘럼 ID)를 저장한다. **고쳤다**(V7, `message_key` 칸) |
| 내용 전체를 `payload`(jsonb)에 복사한다 | 재전송용 `ChunkPayload`와 내용이 두 곳에 있다. `byte[]`가 JSON 안에 Base64로 들어가 더 커진다 | 행에는 배포 ID, 청크 번호, 시도 번호만 두고, 발행할 때 `ChunkPayload`에서 내용을 읽는다 |
| `saga_id`, `saga_status`, `trans_type` 칸이 있다 | 지금은 쓰임새가 없다([ADR 0003](0003-defer-saga.md)) | 지운다. **`saga_id`, `saga_status`는 지웠다**(V6). `trans_type`은 발행 경로를 고르는 데 아직 쓴다 |
| 발행이 끝난 행을 지우지 않는다 | 표가 계속 커진다 | 보관 기간이 지난 행을 지운다. 기간은 시스템 설계 단계에서 정한다 |

### 행에는 내용 대신 참조를 둔다
아웃박스 행에 무엇을 담을지는 두 방식이 있다. 둘 다 실무에서 쓰고, 일반적인 기본값은 전체 저장이다.

| | 방식 | 장점 | 단점 |
|---|---|---|---|
| | 행에 메시지 전체를 저장한다 | 저장 시점의 값이 그대로 나간다. 발행기는 행만 읽으면 된다. CDC로 옮기기 쉽다 | 행이 커진다. 재전송할 때마다 같은 내용이 또 쌓인다 |
| **채택** | **행에는 배포 ID, 청크 번호, 시도 번호만 두고 발행할 때 내용을 읽는다** | 내용이 한 곳에만 있다. 행이 작다 | 발행기가 내용 표를 알아야 한다. 조회가 한 번 더 든다. CDC로 옮기기 어렵다 |

참조 방식을 고른 이유는 셋이다.

1. **행에 쌓이는 양이 부담스럽다.** 전체를 저장하면 시드 기준으로 배포 하나에 약 1.25MB(과목 청크 하나에 약 32KB)가 행에 들어가고, 재전송할 때마다 더 쌓인다. 값은 [인코딩 규칙으로 계산](../system/architecture.md#3-메시지-크기)한 것이다.
2. **어떤 값이 나갔는지를 정확히 남겨야 하는 시스템이 아니다.** 일반적인 이벤트라면 저장 시점의 값을 그대로 보내는 것이 중요하지만, 여기서는 잘못됐으면 원본을 고쳐 다시 배포하면 된다.
3. **다시 조회해도 값이 달라지지 않는다.** 청크 내용은 접수한 뒤 바뀌지 않는다([불변식 4](../domain/model.md#3-불변식)). 그래서 조회 시점의 값이 나가는 참조 방식의 일반적인 위험이 여기에는 없다.

이 이유들은 이 시스템에서만 성립한다. 값이 바뀔 수 있는 데이터나 이력이 중요한 이벤트를 보낼 때는 전체 저장을 기본으로 한다.

### 스케줄러는 한 번에 하나만 돈다
인스턴스가 둘이면 서로 다른 인스턴스가 같은 키의 행을 집어 순서가 뒤집힐 수 있다. Postgres 어드바이저리 락으로 한 번에 한 인스턴스만 발행하게 한다.

`SKIP LOCKED`로 행을 나눠 집는 방식은 쓰지 않는다. 처리량은 늘지만 같은 키의 행이 다른 인스턴스로 갈라진다. 배포는 사람이 요청하는 일이라 처리량보다 순서가 중요하다.

## 결과

### 얻은 것
- 상태 변경과 발행 예약이 한 트랜잭션이라 메시지가 사라지지 않는다.
- 메시지 종류가 늘어도 같은 발행 경로를 쓴다.
- 멈춘 발행을 표에서 바로 볼 수 있다. 오래된 `PENDING` 행이 있으면 Kafka나 스케줄러에 문제가 있는 것이다.

### 감수한 것
- **발행 주기만큼 지연이 생긴다.** 뼈대가 먼저 나가고 그 결과를 받은 뒤 과목이 나가므로, 배포 하나에 발행 주기가 두 번 이상 든다. 지금 주기(10초)는 줄여야 한다.
- **같은 청크가 두 번 나갈 수 있다.** 브로커 응답을 받고 행을 닫기 전에 죽으면 다음 주기에 다시 보낸다. 대상의 반영은 멱등하고 중복 결과는 무시하므로 괜찮다.
- **Kafka 장애 중에 재전송하면 행이 쌓인다.** 복구되면 시도 1과 시도 2가 차례로 나간다. 시도 번호와 멱등한 반영으로 처리된다.
- **실제로 보낸 내용을 나중에 다시 볼 수 없다.** 행에 내용이 없고, 재전송할 수 없는 배포의 내용은 [지운다](../system/architecture.md#청크-내용은-언제까지-두나). 남는 것은 대상이 돌려준 반영 내용(제목, 단원·차시 수)뿐이다. 그 정도로 충분한 시스템이라고 봤다.
- **발행 시점에 내용이 없을 수 있다.** 재전송 중에 늦은 성공이 와서 내용이 먼저 지워진 경우다. 보낼 필요가 없어진 행으로 보고 닫는다.
- **발행 스케줄러가 한 번에 하나라** 많은 배포를 동시에 보내는 데 한계가 있다. 이 시스템의 배포량에서는 문제가 되지 않는다고 본다. 측정해서 확인한다.

## 실무에서는

이 결정은 실무 경험이 아니라 학습 목적에서 골랐다.

## 바꾸려면

**B로 바꾸기**: 청크 표에 발행 시각 칸을 더하고, 스케줄러가 `status = 'SENT' AND published_at IS NULL`을 청크 번호 순서로 읽게 한다. 아웃박스 행을 만드는 곳을 지운다. 메시지 종류가 끝까지 청크 명령 하나뿐이고 표를 줄이고 싶을 때 고려한다.

**전체 저장으로 바꾸기**: 행에 직렬화한 메시지를 담는 칸을 더하고, 행을 만들 때 내용을 함께 넣는다. 발행기는 내용 표를 읽지 않게 된다. 값이 바뀔 수 있는 메시지를 보내게 되거나, 보낸 값을 그대로 남겨야 하는 요구가 생기면 고려한다.

**CDC로 바꾸기**: 아웃박스 테이블을 Debezium 같은 CDC로 읽게 하면 스케줄러와 주기 지연이 사라진다. 다만 CDC는 행의 내용을 메시지로 내보내므로 **참조만 있는 지금 표로는 안 된다.** 전체 저장으로 먼저 바꿔야 한다.
