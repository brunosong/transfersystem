# ADR 0008. [도메인] 저작 시스템을 만들고, 초안과 공개본을 나눈다

- 상태: 채택
- 날짜: 2026-11-20
- 관련 문서: [컨텍스트 맵](../domain/context-map.md), [원본 읽기](../system/source-read.md), [ADR 0002](0002-target-agent.md)
- 관련 모듈: `authoring-service`(새로 만든다), `deployment-service`, `deployment-console`

## 맥락

배포는 저작 시스템(Mongo)의 커리큘럼 문서를 읽어 대상에 보낸다. [컨텍스트 맵](../domain/context-map.md#2-바깥-시스템)에서 저작 시스템은 콘텐츠팀이 주인인 바깥 시스템이다.

이 프로젝트에는 저작 시스템이 없다. 원본 문서는 시드 생성기(`LearningMaterialDataGenerator`)가 한 번에 만들어 넣는다. 그래서 "커리큘럼을 고치고 다시 배포한다"는 흐름을 보여 줄 수 없다.

저작 시스템을 만들 때 실무에서 겪은 두 문제를 함께 푼다.
1. **고치는 중인 커리큘럼이 배포될 수 있다.** 편집하는 문서와 배포가 읽는 문서가 같으면, 반쯤 고친 상태가 그대로 나간다.
2. **여러 명이 같은 커리큘럼을 동시에 고치면 한 사람의 수정이 사라진다.** 나중에 저장한 사람이 앞사람의 수정을 덮어쓴다.

정해야 할 것은 "저작 기능을 어디에 두고, 배포가 무엇을 읽게 하는가"다.

## 선택지

| | 방식 | 고치는 중 배포 | 동시 수정 | 배포 코드 |
|---|---|---|---|---|
| A | 지금대로 시드 생성기만 둔다 | (편집이 없다) | (편집이 없다) | 그대로 |
| B | 저작 서비스가 한 문서를 고치고, 배포가 그 문서를 읽는다 | 막지 못한다 | 따로 풀어야 한다 | 그대로 |
| C | 저작 서비스를 만들고, 배포는 저작 서비스의 API를 부른다 | API가 공개된 것만 주면 막는다 | 따로 풀어야 한다 | 원본 읽기를 다시 짠다 |
| D | 배포 서비스 안에 편집 기능을 넣는다 | 막지 못한다 | 따로 풀어야 한다 | 배포가 원본의 주인이 된다 |
| **E** | **초안과 공개본을 나눈다.** 편집은 초안에만 한다. 공개하면 그 순간의 내용을 판 번호가 붙은 공개본으로 쓴다. 배포는 공개본만 읽는다 | 막는다 | 초안의 버전 칸으로 막는다(낙관적 잠금) | 원본 저장소가 가리키는 컬렉션만 바뀐다 |

## 결정

**E를 쓴다.** 저작은 따로 서비스(`authoring-service`)로 둔다. 성격은 **LCMS**다. 커리큘럼 구조와 판, 공개를 다루고, 차시 안의 내용 자체를 만드는 저작도구는 아니다([용어집](../domain/glossary.md#저작-authoring)).

| 개념 | 뜻 |
|---|---|
| 초안 | 편집하는 문서. 커리큘럼마다 하나. 버전 칸을 두고, 저장할 때 "내가 읽은 버전과 같을 때만" 고친다. 다르면 거절한다 |
| 공개 | 초안의 지금 내용을 공개본으로 고정하는 일 |
| 공개본(판) | 공개할 때마다 하나씩 쌓인다. 판 번호는 1부터 커진다. 한 번 쓴 판은 고치지 않는다 |

지키는 원칙:
1. **배포는 공개본만 읽는다.** 배포에게 공개본 컬렉션은 그냥 원본이다. 저작 서비스가 있다는 것은 모른다.
2. **공개본의 모양은 지금 원본 문서 모양을 따른다.** 원본 변환기(`CurriculumSourceConverter`)가 그대로 읽을 수 있어야 한다. 모양을 바꿔야 하면 바꾸는 곳은 변환기(부패 방지 계층) 하나다.
3. **저작은 배포를 모른다.** 배포 상태를 읽거나, 배포 중이라고 공개를 막지 않는다. 이미 접수한 배포는 접수 때의 내용으로 나간다([불변식 4](../domain/model.md)).

모양:
| | |
|---|---|
| 서비스 | `authoring-service`. 하위 모듈은 deployment-service를 따른다: `authoring-container`, `authoring-domain`(`authoring-domain-core`, `authoring-application-service`), `authoring-dataaccess`(Mongo), `authoring-application`(REST API). 보낼 이벤트가 없으므로 `messaging`은 두지 않는다 |
| 저장소 | Mongo. 초안 컬렉션과 공개본 컬렉션을 나눈다 |
| 화면 | `deployment-console`에 메뉴로 넣는다. 화면은 API를 모아 보여 주는 곳이라 따로 만들 이유가 없다 |

정하지 않은 것: 공개본이 판마다 쌓이므로 배포는 "가장 최근 판"을 읽어야 한다. 원본 읽기가 판 번호로 골라 읽게 할지, "가장 최근 공개본"만 담는 컬렉션을 따로 둘지는 저작 서비스의 시스템 설계에서 정한다.

## 결과

### 얻은 것
- **반쯤 고친 커리큘럼이 나가지 않는다.** 배포는 누군가 공개를 누른 판만 본다.
- **동시 수정에서 수정이 사라지지 않는다.** 늦게 저장한 사람은 덮어쓰는 대신 "다른 사람이 먼저 고쳤다"는 거절을 받고, 새로 읽은 뒤 다시 고친다.
- **배포 코드가 거의 바뀌지 않는다.** 원본 저장소가 공개본 컬렉션을 가리키게 하면 된다.
- **판이 남는다.** 어느 판이 언제 공개됐는지 알 수 있다. 나중에 배포가 몇 번째 판을 보냈는지 기록할 길도 열린다(지금은 하지 않는다).

### 감수한 것
- **개념이 늘어난다.** 초안, 공개, 판을 화면과 문서에서 설명해야 한다.
- **공개본이 계속 쌓인다.** 판이 많아지면 오래된 판을 지우는 규칙이 필요할 수 있다. 지금은 쌓아 둔다.
- **두 서비스가 공개본 모양 하나를 함께 안다.** API(C) 뒤로 숨기지 않았기 때문이다. 원본 저장소로 DB를 읽는 배포의 지금 구조를 지키는 쪽을 골랐다.
- **서비스가 하나 는다.** 빌드, 실행, k8s 배포 대상이 늘어난다.

## 실무에서는

이전에 일한 교육 콘텐츠 회사에서는 배포 시스템이 저작 DB를 직접 읽었다.

- 임시 저장과 공개가 나뉘어 있지 않았다. 편집하는 문서가 곧 배포되는 문서였다.
- 여러 명이 같은 커리큘럼을 동시에 고치는 일이 있었다.

이 프로젝트는 실무를 그대로 따라 하지 않고 이 두 문제를 푸는 쪽을 골랐다. DB를 직접 읽는 구조는 남기되, 배포가 읽는 것을 편집하는 문서가 아니라 고정된 공개본으로 바꿨다.

## 바꾸려면

**C로 가기**: 저작 서비스에 공개본 조회 API를 열고, 배포의 원본 저장소에 "API" 종류를 더한다. 변환기는 API 응답을 읽도록 바꾼다. 초안과 공개본의 구분은 그대로 쓴다.

**B로 되돌리기**: 공개를 없애고 배포가 초안 컬렉션을 읽게 한다. 고치는 중인 커리큘럼이 나갈 수 있다는 것을 받아들여야 한다.
