# ADR 0007. [도메인] 청크끼리 의존을 없애고 과목 청크가 자기 상위를 싣는다

- 상태: 채택
- 날짜: 2026-11-12
- 관련 문서: [도메인 모델](../domain/model.md)(불변식 3, 청크 상태), [이벤트와 메시지](../domain/events.md), [시스템 설계](../system/architecture.md), [원본 읽기 흐름](../system/source-read.md), [ADR 0004](0004-transactional-outbox.md), [ADR 0005](0005-chunks-on-kafka.md)
- 관련 모듈: `deployment-domain-core`의 `ChunkContent`, `Deployment`, `Chunk`, `message-contracts`, `target-agent`

## 맥락

커리큘럼 하나는 뼈대 청크 1개와 과목 청크 N개로 나뉜다([ADR 0005](0005-chunks-on-kafka.md)). 지금 과목 청크에는 학년 ID와 학기 ID만 있고, 학년과 학기 자체(제목, 설명)는 뼈대에만 있다. 대상 DB는 커리큘럼 → 학년 → 학기 → 과목 순으로 부모를 참조한다. 그래서 **과목 청크는 혼자 저장될 수 없고, 뼈대가 먼저 반영되어 있어야 한다.**

이 의존 하나 때문에 다음이 생겼다.

- 불변식 3: 뼈대가 `APPLIED`가 되기 전에는 과목 청크를 보내지 않는다.
- 과목 청크의 `WAITING` 상태와, 뼈대 성공 결과를 받으면 과목을 아웃박스에 넣는 코드. 아웃박스를 두 번에 나눠 쓴다.
- 뼈대가 실패하면 과목 전부가 묶인다. 재전송도 뼈대부터 이어 가야 한다.
- 메시지 순서를 지키려고 아웃박스가 같은 키의 행을 순서대로, 앞 행이 실패하면 뒤 행을 멈추고 보내야 한다([도메인 모델 7절](../domain/model.md#7-메시지-순서)).

지금 코드는 아직 이 규칙을 따르지 않는다. 접수할 때 뼈대와 과목을 모두 한꺼번에 아웃박스에 넣는다. 그래서 과목이 뼈대보다 먼저 도착하면 저장되지 않을 수 있다. 규칙을 코드에 넣기 전에, 이 의존이 꼭 필요한지 다시 본다.

## 선택지

| | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | 의존을 그대로 두고 불변식 3을 구현한다 (지금 문서) | 계약과 대상은 그대로다. 학기 정보가 한 번만 간다 | 위의 상태와 2단계 발행을 모두 만들어야 한다. 배포 상태 기계가 가장 복잡하다 |
| B | 배포를 "구조 배포"와 "내용 배포" 둘로 나누고, 앞의 것이 끝나면 뒤의 것을 시작한다 | 배포 하나 안은 단순하다 | 복잡함이 배포와 배포 사이로 옮겨 갈 뿐이다. 두 배포를 잇는 상태와 코드가 새로 생기고, 운영자가 보는 배포가 둘이 된다 |
| C | 뼈대만 API로 바로 보내고 과목은 Kafka로 보낸다 | 뼈대를 기다리는 시간이 짧다 | 배포 시스템은 Kafka로 청크를 보내기만 하고 반영은 각 서비스가 한다는 경계([컨텍스트 맵](../domain/context-map.md), [ADR 0002](0002-target-agent.md))가 깨진다. 대상마다 API가 필요하다 |
| **D** | **과목 청크가 자기 상위(커리큘럼, 학년, 학기의 제목과 설명)를 함께 싣고, 대상은 상위를 업서트한다** | 청크끼리 의존이 없어진다. 모든 청크를 한꺼번에, 아무 순서로나 보내도 된다 | 계약이 바뀌고, 대상이 상위를 업서트해야 한다. 같은 상위 정보가 여러 청크에 겹쳐 간다 |

## 결정

**D를 쓴다.** 복잡함의 뿌리는 "과목이 혼자 저장될 수 없다"는 것이고, D는 그 뿌리를 없앤다. A와 B는 의존을 관리하는 방법이고, D는 의존을 없애는 방법이다.

### 청크의 모양

| 청크 | 담는 것 | 대상이 하는 일 |
|---|---|---|
| 과목 청크 (1번부터) | 커리큘럼·학년·학기의 ID, 제목, 설명 + 과목 하나와 그 아래 단원·차시 전부 | 커리큘럼, 학년, 학기를 업서트한 뒤 과목을 업서트한다 |
| 정리 청크 (0번, 지금의 뼈대) | 커리큘럼·학년·학기 구조와 학기별 과목 ID 목록 | 상위를 업서트하고, 목록에 **없는** 과목을 서비스에서 뺀다 |

- 0번은 이름만 남는다. 하는 일은 "원본에서 지운 과목 빼기"다([이벤트와 메시지 6절](../domain/events.md#6-원본에서-지운-과목은-대상에서도-뺀다)). 과목이 하나도 없는 커리큘럼도 0번 하나로 반영된다.
- 정리 청크도 순서와 상관없다. "목록에 없는 과목을 뺀다"는 규칙이라 새 과목은 목록에 있으므로, 먼저 오든 나중에 오든 지워지지 않는다.
- 한 배포의 청크는 모두 같은 원본에서 나온다(불변식 4). 그래서 여러 청크에 실린 같은 학기의 제목이 서로 다를 일이 없다. 어느 것이 마지막에 써져도 결과가 같다.

### 바뀌는 규칙

| 규칙 | 전 | 후 |
|---|---|---|
| 불변식 3 | 뼈대가 `APPLIED`가 되기 전에는 과목을 보내지 않는다 | **지운다.** 접수할 때 모든 청크를 보낸다 |
| 청크 상태 | `WAITING` → `SENT` → `APPLIED`/`FAILED` | `SENT` → `APPLIED`/`FAILED`. `WAITING`을 지운다 |
| 결과 처리 | 뼈대 성공이면 기다리던 과목을 보낸다 | 결과를 기록하고 배포 상태만 정한다 |
| 아웃박스 순서 | 같은 키의 앞 행이 실패하면 뒤 행을 멈춘다 | 순서를 지킬 필요가 없다. 명령의 Kafka 키(대상 + 커리큘럼 ID)는 옛 배포와 새 배포의 순서를 위해 그대로 둔다 |
| 대상 규칙 | 과목은 학기가 있어야 저장된다 | 과목 청크 하나로 상위까지 저장된다 |

## 결과

### 얻은 것
- 배포 상태 기계가 단순해진다. `WAITING`, 뼈대 성공으로 시작하는 2단계 발행, 아웃박스의 순서 멈춤이 없어진다.
- 뼈대 하나가 실패해도 과목이 묶이지 않는다. 실패한 청크만 다시 보낸다.
- 지금 코드가 이미 하는 "접수할 때 모두 아웃박스에 넣기"가 맞는 동작이 된다.

### 감수한 것
- **메시지 계약이 바뀐다.** `SubjectContent`에 커리큘럼·학년·학기의 제목과 설명을 더한다. 기본값이 있는 칸을 더하는 것이라 호환성 `FULL`은 지킨다. 대상은 새 칸을 읽도록 고친다.
- **대상의 일이 는다.** 과목을 반영할 때마다 상위 세 단계를 업서트한다. 학기 하나에 과목이 5개면 같은 학기 행을 5번 덮어쓴다. 시드 커리큘럼 하나에 업서트가 수십 번 는다. 과목 하나에 차시 500행을 쓰는 것에 비하면 작다.
- **메시지가 조금 커진다.** 시드 기준으로 과목 청크 하나에 약 0.1KB(0.3%)다. 학년·학기 설명이 각각 500자라도 약 3KB다. 900KB 제한([시스템 설계 3장](../system/architecture.md#3-메시지-크기))에 영향이 없다. 크기를 키우는 것은 차시 설명이다.
- **상위만 바뀐 경우도 과목 청크가 모두 간다.** 학기 제목 하나만 고쳐도 배포는 커리큘럼 전체를 보낸다. 지금도 배포 단위가 커리큘럼 전체라 달라지는 것은 없다.

## 실무에서는

이전 교육 콘텐츠 회사의 시스템에는 **레벨별로 보낼 수 있는 기능**이 있었다. 학년, 학기, 과목 같은 단계를 골라 그 단계만 보내는 식이다. 이것은 **상위가 대상에 이미 있다는 가정** 위에서 움직였고, 그 가정 아래에서는 크게 문제가 없었다.

이번 시스템은 그 가정을 할 수 없다. 새 커리큘럼을 처음 보내거나 새 대상에 처음 보낼 때는 상위가 없다. 그래서 "상위가 있다고 가정한다" 대신 **"청크가 자기 상위를 들고 간다"**로 바꿨다. 가정이 맞는지를 순서로 지키는 것(A)보다, 가정 자체가 필요 없게 만드는 쪽(D)을 골랐다.

## 바꾸려면

- 상위가 커져서 청크마다 싣기 부담스러워지면(예: 학기에 큰 속성이 붙는다), 상위는 ID만 싣고 대상이 없는 상위를 빈 행으로 만들어 두게 할 수 있다. 상위 내용은 정리 청크가 채운다. 이 방식도 순서 의존은 없다.
- 레벨별 배포(과목 하나만 보내기 같은)를 넣을 때도 이 결정은 그대로 쓸 수 있다. 과목 청크가 혼자 저장되므로 과목 하나만 보내도 된다.
- 순서 의존이 다시 필요해지는 경우(예: 대상이 상위를 직접 만들 수 없는 시스템)에는 A로 돌아간다. 이때 [도메인 모델](../domain/model.md)의 불변식 3과 `WAITING` 설계를 되살린다.
