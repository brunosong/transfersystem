# ADR 0006. [시스템] 청크 내용 계약은 계층을 타입으로 두고 세부 속성은 JSON 문자열로 보낸다

- 상태: 채택
- 날짜: 2026-11-11
- 관련 문서: [이벤트와 메시지](../domain/events.md), [ADR 0001](0001-message-contract-distribution.md), [ADR 0005](0005-chunks-on-kafka.md)
- 관련 모듈: `message-contracts`, `deployment-domain-core`의 `ChunkContent`, `CurriculumSourceConverter`, `deployment-messaging`

## 맥락

배포 시스템은 저작 문서(Mongo)를 읽어 청크로 나누고, 대상은 받은 청크를 자기 테이블의 컬럼에 하나씩 나눠 넣는다. 정할 것은 **대상이 받는 내용의 모양을 누가 정하느냐**다.

지금은 학년, 학기, 과목, 단원, 차시의 모든 칸을 타입(record와 Avro 스키마)으로 정해 두었다. 그래서 저작 문서에 칸이 하나 늘면 보내는 쪽 네 곳을 고친다. record, 변환기, Avro 매퍼, `.avsc`다.

칸이 늘 때 대상이 그 칸을 쓰려면 어느 방식이든 대상은 고쳐야 한다. 컬럼에 나눠 넣기 때문이다. 줄일 수 있는 것은 보내는 쪽 비용이다.

## 선택지

| | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | 모든 칸을 타입으로 정한다 (지금) | 빠진 칸은 접수할 때 거절된다. 저작 쪽이 칸 이름을 바꿔도 변환기만 고치면 된다 | 속성 하나가 늘 때마다 보내는 쪽 네 곳과 대상을 고친다 |
| B | 계층만 자르고 내용은 원본 JSON 그대로 보낸다 | 보내는 쪽은 고칠 게 거의 없다 | 대상이 저작 문서의 모양에 묶인다. 칸 이름이 바뀌면 대상이 조용히 깨진다. 계층에서도 빠진 칸이 대상에 가서야 드러난다 |
| **C** | **계층은 타입으로, 단원과 차시의 세부 속성은 JSON 문자열 칸 하나로 보낸다** | 속성이 늘어도 보내는 쪽은 그대로다. 계층에는 A의 장점이 남는다 | 세부 속성은 접수할 때 검사하지 않는다 |

## 결정

**C를 쓴다.**

### 어느 칸을 어디에 두나

| 칸 | 둘 곳 |
|---|---|
| 모든 단계의 `id`, `title`, `description` | 타입 |
| 차시의 `lessonNumber` | 타입. 순서라서 구조에 가깝다 |
| 차시의 `learningLevel` | `attributes`. 세부 속성이다 |
| 단원과 차시의 나머지 원본 칸 | `attributes` |

- 변환기는 **아는 칸과 자식 목록(단원의 `lesson`)을 뺀 나머지를 모두 `attributes`에 담는다.** 저작 쪽에 속성이 늘어도 변환기를 고치지 않는다.
- `attributes`는 Avro `string`이고, 값은 JSON 객체 하나다. 속성이 없으면 `"{}"`를 보내고 null은 쓰지 않는다.
- 학년, 학기, 과목에는 `attributes`를 두지 않는다. 그 단계의 속성이 늘어나는 일이 생기면 그때 같은 방식으로 더한다. 기본값 `"{}"`를 주면 옛 대상은 깨지지 않는다.
- Mongo의 날짜는 ISO-8601(UTC) 문자열(`"2026-11-11T00:00:00Z"`), ObjectId는 16진 문자열로 바꾼다. 대상이 Mongo 전용 모양(`{"$date": ...}`, `{"$oid": ...}`)을 몰라도 되게 하려는 것이다. 원본 문서는 Map을 거치지 않고 드라이버의 `Document.toJson`이 이 규칙으로 바로 JSON을 쓴다(`MongoConnectHelper`).

### 바꾸는 순서

받는 쪽(`target-agent`)이 Avro의 `learningLevel`을 읽어 컬럼에 넣고 있다. 한 번에 지우면 받는 쪽이 깨지고, 기본값 없는 칸을 지우는 것이라 호환성 `FULL`도 깨진다. 그래서 넓히고, 옮기고, 좁히는 순서로 바꾼다.

| 단계 | 할 일 | 상태 |
|---|---|---|
| 1. 넓히기 | `attributes`(기본값 `"{}"`)를 더하고 `learningLevel`에 기본값 `0`을 준다. 보내는 쪽은 두 곳 모두에 싣는다 | 완료 |
| 2. 옮기기 | 받는 쪽이 `learningLevel`을 `attributes`에서 읽는다 | |
| 3. 좁히기 | 스키마, `ChunkContent`, 변환기에서 `learningLevel`을 지운다. 기본값이 있으니 `FULL`을 지킨다 | |

### JSON 문자열을 고른 이유

Avro `map<string>`도 검토했다. 하지만 이 방식은 값이 모두 문자열이 된다. `3`이 `"3"`으로 가서 대상이 다시 바꿔야 하고, 배열과 중첩도 담기 어렵다. JSON 문자열은 숫자, 배열, 중첩이 그대로 가고, 대상은 Jackson으로 읽어 컬럼에 나눠 넣으면 된다.

## 결과

### 얻은 것
- 차시와 단원의 속성이 늘어도 보내는 쪽은 고칠 곳이 없다. 대상만, 그 속성을 쓸 때 컬럼 매핑을 더한다.
- 계층의 칸은 여전히 접수할 때 검사한다. 칸 이름이 바뀌어도 대상은 그대로다.
- 타입으로 정한 칸이 적어져 Avro 스키마와 매퍼가 단순해진다.

### 감수한 것
- **세부 속성은 대상에 가서야 문제가 드러난다.** 저작 쪽이 속성 이름을 바꾸면 대상의 그 컬럼이 조용히 빈다. 이전 시스템과 같은 위험이지만 이제 세부 속성에만 남는다.
- **`attributes` 안의 칸은 계약 문서에 드러나지 않는다.** 어떤 속성이 오는지는 저작 문서를 보고 알아야 한다.
- **메시지가 조금 커진다.** JSON 문자열은 칸 이름을 매번 싣는다. 크기 제한([ADR 0005](0005-chunks-on-kafka.md))은 실제 Avro 바이트로 재므로 이것까지 포함된다.

## 실무에서는

이전 교육 콘텐츠 회사의 시스템은 DB가 직접 연결되어 있었다. DB에서 꺼낸 데이터를 Map에 담고, 칸을 하나씩 꺼내 대상 테이블의 컬럼에 나눠 넣었다. 자주 바뀐 것은 **차시와 단원의 세부 속성**이었다. 학년, 과목, 단원 같은 계층은 거의 바뀌지 않았다.

그래서 바뀌지 않는 계층은 타입으로 굳히고, 자주 바뀌는 속성은 흘려보내도록 나눴다.

## 바꾸려면

**어떤 속성을 타입으로 올리기**: 대상이 꼭 써야 하거나 검사가 필요한 속성이 생기면 Avro에 기본값을 둔 칸으로 더하고, 변환기의 "아는 칸"에 넣어 `attributes`에서 뺀다. 옛 대상이 깨지지 않도록, 한동안은 두 곳에 모두 싣는 것도 고려한다.

**A로 돌아가기**: 세부 속성이 거의 바뀌지 않게 되거나 모든 칸을 접수 때 검사해야 하면, `attributes`의 칸을 하나씩 타입으로 올린 뒤 `attributes`를 지운다.
