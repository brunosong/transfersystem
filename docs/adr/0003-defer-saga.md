# ADR 0003. [시스템] 사가 구현을 뒤로 미룬다

- 상태: 채택 (보류 결정. 나머지를 다 만든 뒤 다시 본다)
- 날짜: 2026-11-04
- 관련 문서: [도메인 모델](../domain/model.md), [ROADMAP](../ROADMAP.md)

## 맥락

처음 로드맵의 최종 목표는 "커리큘럼 하나를 온라인캠퍼스와 부트캠프에 함께 반영하고, 뒤 단계가 실패하면 앞 단계를 되돌리는 오케스트레이션 사가"였다.

사가는 여러 곳에 걸친 작업을 **전부 성공하거나 전부 되돌려야 할 때** 쓴다. 도메인 모델을 정하고 나서 보니, 지금 시스템에는 그런 작업이 없다.

- 배포 하나의 대상은 하나다. 걸쳐 있는 작업이 없다.
- 일부만 반영된 배포는 되돌리지 않고 재전송으로 끝까지 밀고 나간다.
- 온라인캠퍼스와 부트캠프는 별개 서비스다. 한쪽 배포가 실패해도 다른 쪽 학습자에게 문제가 없고, 실패한 쪽만 다시 보내면 된다.

즉 사가는 업무 요구에서 나온 항목이 아니라 패턴을 배우려고 넣은 항목이었다.

## 선택지

| | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | 계획대로 지금 구현한다 | 사가의 어려운 부분(보상, 멱등성, 타임아웃)을 일찍 배운다 | 업무 이유 없이 복잡도가 크게 는다. before-image, inbox, 오케스트레이터 테이블이 생기고 아직 만들지 않은 배포 모델을 그 위에 얹어야 한다 |
| **B** | **뒤로 미룬다** | 배포 모델, 화면, 에이전트 떼어 내기에 집중한다. 필요한 보장(응답 기한, 재전송, 동시 배포 막기)은 사가 없이 얻는다 | 사가 학습이 늦어진다 |
| C | 계획에서 아예 지운다 | 가장 단순하다 | 나중에 배우고 싶을 때 지금까지 한 설계를 다시 찾아야 한다 |

## 결정

**B를 쓴다.** 사가를 지금 구현하지 않고, 다른 일을 모두 마친 뒤 할지 다시 정한다. 그동안 설계 내용은 ROADMAP 맨 아래 "나중에" 절에 그대로 둔다.

사가 때문에 계획돼 있던 일 가운데 사가 없이도 필요한 것은 ROADMAP Phase 3 "배포 모델 구현"으로 옮긴다.

| 일 | 어떻게 되나 |
|---|---|
| 응답 기한, 동시 배포 막기, 상태 조회, 결과 처리의 멱등성 | **유지** ([모델](../domain/model.md)에 정의) |
| 대상의 멱등한 반영, 일시적 오류와 업무 오류 구분 | **유지** (재전송에 필요) |
| 아웃박스 개선 | **유지** (형태는 따로 정한다) |
| 오케스트레이터, 사가 상태 테이블 | 보류 |
| 보상, before-image, `migration_snapshot` | 보류 |
| inbox | 보류 (업서트로 멱등성을 얻을 수 있는지 먼저 본다) |

## 결과

### 얻은 것
- 지금 필요한 모델이 단순해진다. 배포 상태는 셋, 청크 상태는 넷으로 끝난다.
- 면접에서 "왜 사가가 필요했나요?"에 억지로 답하지 않아도 된다. 대신 "검토했더니 지금은 필요 없어서 미뤘다"고 근거를 들어 말할 수 있다.

### 감수한 것
- **잘못 배포해도 되돌리는 기능이 없다.** 고치려면 원본을 고쳐 다시 배포해야 한다. 원본에서 지운 과목도 대상에서 빠지므로([ADR 0006](0006-remove-deleted-subjects.md)), 실수로 지운 과목은 원본을 되살려 다시 배포할 때까지 서비스에 없다.
- 사가 패턴은 당분간 직접 경험하지 못한다.
- `sagaId`, `SagaStatus`, `infrastructure/saga` 같은 흔적이 코드에 남아 있다. 지금은 쓰임새가 없으므로 Phase 3에서 정리한다.

## 실무에서는

이 결정에 해당하는 실무 경험은 없다. 사가는 실무 요구가 아니라 학습 목적에서 나온 항목이다.

## 바꾸려면

아래 중 하나가 생기면 사가를 다시 검토한다.
- **업무 요구**: 한 커리큘럼이 모든 서비스에 같이 반영되지 않으면 문제가 생기는 경우
- **되돌리기 요구**: 잘못 배포했을 때 이전 내용으로 돌려야 하는 경우. 이건 사가 없이 "이전 배포 내용으로 재배포"로 풀 수 있는지 먼저 본다
- **학습 목적**: 나머지를 다 만든 뒤, 사가를 직접 구현해 보고 싶을 때. 이때는 업무 이유가 약하다는 점을 문서에 그대로 적는다

다시 시작할 때 확인할 것: ROADMAP의 사가 설계는 Kafka 키를 `sagaId`로 정했다. 지금 명령의 키는 [대상 + 커리큘럼 ID](../domain/model.md#7-메시지-순서)이므로, 두 대상에 걸친 순서를 어떻게 보장할지 다시 정해야 한다.
