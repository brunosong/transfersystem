# ADR 0010. [시스템] 대상 DB에는 한 번에 한 건씩, 정한 간격으로만 쓴다

- 상태: 제안 (아래 "확인할 실험"을 로컬에서 재현해 보고 채택한다)
- 날짜: 2026-11-26
- 관련 문서: [시스템 설계 4장 Kafka 토픽](../system/architecture.md#4-kafka-토픽), [5장 응답 기한](../system/architecture.md#응답-기한을-어떻게-정했나), [ADR 0002](0002-target-agent.md), [ADR 0005](0005-chunks-on-kafka.md)
- 관련 모듈: `target-agent`

## 맥락

배포는 운영 중인 서비스 DB(대상 DB)에 쓴다. 서비스가 사용자 요청을 받는 그 DB다. 배포가 DB를 바쁘게 만들면 서비스가 느려진다.

실무(교육 콘텐츠 회사)에서 Kafka를 넣기 전에는 원본 DB에서 대상 DB로 바로 밀어 넣었다. 한꺼번에 들어가니 대상 DB에 부하가 몰렸고, **운영 시간에는 배포를 할 수 없었다.** 그래서 Kafka를 넣으면서 "피크 시간에도 대상 DB에 최소한의 부하만 주는 것"을 목표로 삼았다.

지금 코드는 이 목표를 지키지 못한다.

- 토픽은 3파티션이고, target-agent는 컨슈머 스레드 3개(`concurrency: 3`)로 읽는다. **키가 다른 파티션에 떨어진 명령끼리는 대상 DB에 최대 3건이 동시에 들어간다.** 키가 다르다고 늘 다른 파티션에 가는 것은 아니다(`murmur2(키) % 파티션 수`라서 겹칠 수 있다. 아래 실험 1).
- 처리 속도에는 제한이 없다. target-agent의 `Thread.sleep(1000)`은 로컬 H2가 너무 빨라 흐름이 보이지 않아서 넣은, 실제 DB 처리 시간(약 1초)의 흉내다. 속도 제한이 아니고, 숫자로 박혀 있어 의도도 보이지 않는다.

정할 것은 두 가지다. **동시에 몇 건을 쓰는가**, 그리고 **얼마나 빨리 쓰는가**다.

### 파티션과 컨슈머, 무엇이 동시 처리 수를 정하나

실무에서는 파티션을 하나로 두어 하나씩 처리되게 했다. 그런데 **동시에 처리하는 수는 컨슈머(스레드) 수가 정한다.** 파티션 수는 그 상한일 뿐이다.

- 파티션 1개: 컨슈머를 몇 개 띄워도 1개만 일한다.
- 파티션 3개 + 컨슈머 1개: 그 하나가 세 파티션을 번갈아 읽으며 하나씩 처리한다.

둘 다 "한 번에 하나"다. 다른 점은 **나중에 바꾸는 비용**이다. 파티션은 늘리면 같은 키가 다른 파티션으로 옮겨 가서 키 안의 순서가 흔들린다. 컨슈머 수는 설정 숫자 하나다.

## 선택지

### 동시에 몇 건을 쓰는가

| | 방법 | 대상 DB 동시 쓰기 | 감수할 것 |
|---|---|---|---|
| A | 지금처럼 컨슈머 3개 | 최대 3건 | 피크 시간의 부하를 막지 못한다 |
| B | 파티션을 1개로 | 1건 | C와 효과가 같은데, 나중에 병렬이 필요해 늘리면 키 순서가 흔들린다 |
| **C** | **파티션은 두고 컨슈머를 1개로** | **1건** | 대상끼리도 한 줄로 선다(아래 결과) |

### 얼마나 빨리 쓰는가

| | 방법 | 감수할 것 |
|---|---|---|
| 가 | 제한 없음 | 컨슈머 하나라도 쉬지 않고 최대한 빨리 쓴다. "하나씩"이지 "천천히"가 아니다 |
| 나 | 처리 코드 안에서 쉬기 (지금의 `Thread.sleep`) | 쉬는 시간이 처리 시간에 섞여 잴 수 없다. 숫자가 코드에 박혀 환경마다 바꿀 수 없다 |
| **다** | **컨슈머가 가져가는 간격으로 조절** (`max-poll-records: 1` + `idle-between-polls`) | 가져가지 않은 명령은 토픽에서 기다린다. 응답 기한을 다시 계산해야 한다 |
| 라 | 브로커 쿼터(`consumer_byte_rate`) | 바이트 기준이라 "건수"를 다루기 어렵다. 브로커 설정이라 서비스 팀이 바꾸기 어렵다 |

## 결정

**C와 다를 함께 쓴다.**

1. **대상 DB에 동시에 쓰는 것은 1건이다.** 파티션은 줄이지 않고, 컨슈머 수로 지킨다.
   - 지금(토픽 하나): target-agent의 `concurrency`를 1로 둔다.
   - [대상별 토픽](../system/architecture.md#대상별로-나눌-것인가)으로 나눈 뒤: **대상마다** 컨슈머 1개를 둔다. 동시 1건은 대상 DB 하나에 대한 약속이지, 모든 대상을 합친 약속이 아니다.
2. **속도는 컨슈머가 가져가는 간격으로 조절한다.** 한 번에 1건(`max-poll-records: 1`, 지금과 같음)을 가져오고, 가져오기 사이에 `idle-between-polls`만큼 쉰다. 값은 설정으로 둔다.
   - 운영 값은 대상 DB의 한 건 처리 시간을 재서 정한다.
   - 로컬은 1초로 둔다. 흐름을 눈으로 보려는 `Thread.sleep(1000)`의 일을 이 설정이 대신하고, sleep은 지운다.
3. **파티션 수는 이 결정과 따로 간다.** 파티션은 "나중에 늘릴 수 있는 동시 처리 수의 상한"으로만 쓴다. 대상별 토픽을 6파티션으로 넉넉히 잡는다는 시스템 설계 4장은 그대로다. 지금의 3파티션 토픽은 대상별로 나눌 때 함께 바뀐다.

### 확인할 실험

이 결정은 머릿속 추론이다. 실무에서도 "파티션이 하나여야 천천히 간다"고 믿었다가 이번에 다시 보고 틀렸을 수 있다고 알게 됐다. 그래서 **각 경우를 로컬에서 재현해 보고**, 결과를 여기에 적은 뒤 채택한다. 대상 DB에 몇 건이 동시에 들어가는지는 target-agent 로그(스레드, 시작·끝 시각)와 Kafka UI의 컨슈머 랙으로 본다.

| # | 설정 | 예상 | 결과 |
|---|---|---|---|
| 1 | 파티션 3, 컨슈머 3 (지금) | 다른 커리큘럼끼리 동시에 쓴다 | **예상이 틀렸다(2026-11-26).** `ONLINE_CAMPUS:DEV:CUR001`~`CUR004`는 해시가 겹쳐 모두 2번 파티션에 들어갔다. CUR002와 CUR003을 함께 보내자 2번을 맡은 컨슈머 하나만 18건을 한 줄로 처리했다(로그의 스레드 이름 하나, `동시=1`). 나머지 둘은 놀았다. 키가 다른 파티션에 떨어질 때만 나뉜다: CUR005를 두 대상에 보내자 0번과 1번 파티션에 들어가 서로 다른 컨슈머가 맡았다. 둘은 실제로 겹쳐 돌았다: 1번 파티션 스레드(`ntainer#0-1-C-1`)가 시작할 때 `동시=2`였다. 0번 파티션의 BOOTCAMP 건이 아직 처리 중이었다 |
| 2 | 파티션 1, 컨슈머 3 | 한 스레드만 일하고 둘은 논다 | |
| 3 | 파티션 3, 컨슈머 1 | 1번과 같은 양을 하나씩 처리한다. 2번과 속도가 같다 | |
| 4 | 3번 + 가져가는 간격 0초 / 1초 / 3초 | 간격만큼 느려지고, 그동안 랙이 쌓인다 | |
| 5 | 4번의 긴 간격 + 짧은 응답 기한 | 대상은 성공하는데 응답 없음(`NO_REPLY`)이 된다 | **예상대로(2026-11-26, 간격 대신 컨슈머를 꺼서 재현).** target-agent를 끈 채 뼈대 명령 3건을 넣고 10분 넘게 두자 응답 기한(10분)이 지나 배포 3개가 `FAILED`가 됐다. 그 뒤 컨슈머를 켜자 뼈대가 반영되어 늦은 성공으로 뼈대만 `APPLIED`가 됐고, 과목은 나가지 않았다. 버퍼에 오래 쌓이면 대상이 멀쩡해도 기한에 걸린다 |
| 6 | 배포가 도는 중에 파티션을 3에서 6으로 늘린다 | 같은 키가 다른 파티션으로 가서 순서가 흔들릴 수 있다 | |

## 결과

### 얻은 것

- **배포는 일부러 천천히 간다.** 빨리 끝내는 것보다 서비스를 느리게 만들지 않는 것이 목표다. 시드 커리큘럼 하나(청크 9개)는 적어도 9 × (처리 시간 + 쉬는 간격)이 걸리고, 배포 여러 개를 함께 걸면 그만큼 줄을 선다. 운영 시간에 배포하지 못하던 것보다 낫다.
- **배포가 대상 DB에 주는 부하의 상한이 정해진다.** 대상 DB 하나는 한 번에 1건씩, 정한 간격으로만 받는다. 피크 시간에도 배포를 걸어 둘 수 있다.
- **Kafka가 버퍼 역할을 한다.** 가져가지 않은 명령은 토픽에 남는다. 배포를 한꺼번에 많이 걸어도 대상 쪽은 같은 속도로 받는다.
- **속도를 코드 없이 바꾼다.** 피크 시간에 더 늦추거나 야간에 빠르게 하는 것이 설정 하나다.
- **로컬의 흉내가 이름을 얻는다.** `Thread.sleep(1000)`이 무엇을 위한 것인지 설정 이름으로 드러난다.

### 감수한 것

- **토픽을 나누기 전까지는 대상끼리도 한 줄로 선다.** 컨슈머가 하나라 부트캠프 DEV 명령이 처리되는 동안 온라인캠퍼스 PROD 명령도 기다린다. 지금도 같은 파티션 안에서는 그랬지만, 이제는 모든 파티션에서 그렇다. 대상별 토픽으로 나누면 풀린다.
- **응답 기한을 다시 계산해야 한다.** 기한은 `SENT`부터 재므로, 앞에 줄 선 청크 수 × (처리 시간 + 쉬는 간격)이 기한 안에 들어와야 한다. 그렇지 않으면 대상은 멀쩡한데 응답 없음(`NO_REPLY`)이 된다. [시스템 설계 5장](../system/architecture.md#응답-기한을-어떻게-정했나)의 공식에 쉬는 간격을 넣는다.
- **`max.poll.interval.ms` 안에서 쉬어야 한다.** 쉬는 간격은 다음 가져오기까지의 시간이라, 이 값(지금 30분)을 넘기면 그룹에서 쫓겨난다. 초 단위 간격에서는 문제가 없다.

## 실무에서는

Kafka 이전에는 DB에서 DB로 바로 넣어서 운영 시간에는 배포를 할 수 없었다. Kafka를 넣으면서 **파티션을 하나로 두고, 컨슈머가 가져가는 속도를 조금 늦춰서** 대상 DB가 천천히 하나씩 받게 했다. 피크 시간에도 최소한의 부하만 주려는 것이었다.

이번에 다시 보니 "하나씩"을 만든 것은 파티션이 아니라 컨슈머 수였다. 그래서 같은 목표를 지키면서, 나중에 바꾸기 어려운 파티션 대신 바꾸기 쉬운 컨슈머 수와 가져가는 간격으로 옮겼다. 그리고 그 약속을 "모든 대상을 합쳐 하나"가 아니라 "대상 DB마다 하나"로 좁혔다.

## 바꾸려면

- **대상 DB가 더 받아도 되면:** 그 대상의 컨슈머 수를 늘린다. 파티션 수까지는 설정만 바꾸면 된다. 키가 같은 명령의 순서는 파티션이 지키므로 깨지지 않는다.
- **시간대에 따라 속도를 바꾸고 싶으면:** 쉬는 간격을 시간대별로 바꾸거나, 피크 시간에는 리스너를 멈추는(`pause`) 일정을 둔다. 지금은 하지 않는다.
- **간격보다 정확한 제한이 필요하면:** 초당 건수를 세는 제한기(rate limiter)를 처리 앞에 둔다.
