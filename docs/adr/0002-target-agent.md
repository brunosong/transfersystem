# ADR 0002. [도메인] 대상 반영을 떼어 낼 수 있는 대리 구현(대상 에이전트)으로 둔다

- 상태: 채택
- 날짜: 2026-11-03
- 관련 문서: [컨텍스트 맵](../domain/context-map.md), [용어집](../domain/glossary.md)
- 관련 모듈: `transfer-service`(→ `deployment-service`), `data-migration-service`(→ `target-agent`)

## 맥락

배포는 원본의 커리큘럼을 서비스 시스템(온라인캠퍼스, 부트캠프)의 DB에 반영하는 일이다.

**원래 맞는 모델**은 서비스 팀이 각자 Kafka 컨슈머를 두고, 배포 시스템이 보낸 청크를 받아 자기 DB에 반영하는 것이다. 자기 DB의 스키마와 규칙을 아는 것은 그 팀뿐이기 때문이다.

**지금 상황**은 서비스 팀이 컨슈머를 개발할 수 없다. 그래도 배포는 돌아가야 한다. 누군가는 그 팀들 대신 서비스 DB에 써야 한다.

정해야 할 것은 "대신 쓰는 코드를 **어디에, 어떤 모양으로** 두는가"다. 이 결정에 따라 다음이 갈린다.
- 서비스 DB 접속 정보가 어디에 모이는가 (보안 피해 범위)
- 나중에 서비스 팀이 가져갈 때 배포 시스템을 얼마나 고쳐야 하는가
- 대상의 상태와 반영 결과를 어떻게 아는가

## 선택지

| | 방식 | 장점 | 단점 |
|---|---|---|---|
| A | **중앙 직접 접근**: 배포 시스템이 모든 서비스 DB 접속 정보를 갖고 직접 쓰고 읽는다 | 만들기 가장 쉽다. 대상 DB를 바로 읽으니 상태와 결과를 즉시, 정확하게 안다. | **한 곳이 뚫리면 모든 서비스 DB가 열린다.** 서비스 스키마가 바뀔 때마다 배포 시스템을 고친다. 서비스 팀이 가져가려면 배포 시스템을 뜯어야 한다. |
| **B** | **대상 에이전트 + 대상 연동 계약**: 배포 시스템은 계약(명령·결과·조회)만 연다. 서비스 팀 대신 계약을 구현하는 에이전트를 따로 둔다. | 배포 시스템은 서비스 DB 접속 정보를 하나도 갖지 않는다. 서비스 팀이 계약을 구현하면 그 대상만 에이전트에서 빼면 된다. 대상이 늘어도 배포 코드는 그대로다. | 계약, 토픽, 결과 메시지를 설계하는 일이 늘어난다. 기본 검증이 대상이 **보고한** 결과에 기댄다. |
| C | **서비스 팀이 만들 때까지 기다린다** | 처음부터 맞는 모양이다. 우리가 서비스 DB를 만질 일이 없다. | 그동안 배포를 할 수 없다. 서비스 팀 일정에 묶인다. |

## 결정

**B를 쓴다.** 대상 반영은 서비스 팀 컨슈머의 **대리 구현**으로 보고, 배포 컨텍스트 밖의 **대상 에이전트(`target-agent`)**에 둔다.

지키는 원칙:
1. **배포 시스템은 에이전트가 있다는 것을 모른다.** 결과를 에이전트가 보냈는지 서비스 팀 컨슈머가 보냈는지 구분하지 않는다.
2. **떼어 내도 남아야 하는 것은 에이전트에 두지 않는다.** 대상 목록, 배포 허용, 배포 기록, 검증은 배포 컨텍스트에 둔다.
3. **대상과의 약속은 대상 연동 계약 하나다.** 서비스 팀이 이 계약만 읽고 자기 컨슈머를 만들 수 있어야 한다. 에이전트만 아는 지름길(대상 DB 직접 읽기)에 기대는 기능은 배포 쪽에 만들지 않는다.

대상 연동 계약:
| | 계약 | 필수 |
|---|---|---|
| 1 | 자기 대상 앞으로 온 반영 명령을 받아 멱등하게 반영한다 | 필수 |
| 2 | 청크마다 결과를 돌려준다. 성공이면 무엇을 반영했는지(과목 ID, 단원·차시 수)도 담는다 | 필수 |
| 3 | 커리큘럼 ID로 지금 들어 있는 트리를 조회해 준다 | 선택 |

## 결과

### 얻은 것
- **보안 피해 범위가 줄어든다.** 배포 시스템이 뚫려도 서비스 DB는 열리지 않는다. 할 수 있는 일은 계약에 있는 명령을 보내는 것뿐이다.
- **의존 방향이 맞다.** 핵심(배포)이 임시 구현(에이전트)에 기대지 않는다. 임시 구현을 치워도 핵심은 고치지 않는다.
- **떼어 내기가 설정 수준의 일이 된다.** 대상 시스템마다 명령 토픽을 나눠 두면, 그 토픽의 컨슈머만 서비스 팀 것으로 바꾸면 된다.
- **대상이 늘어도 배포 코드를 고치지 않는다.** 새 대상은 계약을 구현한 컨슈머(또는 에이전트 어댑터)를 하나 더 둘 뿐이다.

### 감수한 것
- **설계할 것이 늘어난다.** 계약 문서, 대상별 토픽, 결과 메시지의 반영 내용, 대상 목록 이전.
- **기본 검증이 보고에 기댄다.** A는 대상 DB를 직접 읽으니 배포 뒤에 누가 데이터를 고쳤는지까지 잡는다. B의 기본 검증은 대상이 "이만큼 넣었다"고 보고한 내용을 믿는다. 에이전트가 맡은 동안은 조회 계약(3)을 제공해서 A 수준의 검증을 유지한다.
- **대상 상태를 DB 연결로 볼 수 없다.** 결과가 제때 돌아오는지(마지막 결과 시각, 응답 없는 청크 수)로 본다.
- **에이전트가 있는 동안 위험은 에이전트로 옮겨 갈 뿐이다.** 그래서 아래 "피해 범위를 줄이는 장치"를 함께 둔다.

### 피해 범위를 줄이는 장치
| 장치 | 효과 |
|---|---|
| 대상마다 에이전트를 따로 띄운다 | 온라인캠퍼스 에이전트가 털려도 부트캠프 DB는 안전하다 |
| 에이전트의 DB 계정에는 커리큘럼 관련 테이블 쓰기 권한만 준다 | 털려도 회원 정보 같은 다른 테이블은 읽을 수 없다 |
| 배포 시스템에는 대상 접속 정보를 두지 않는다 | 배포 시스템이 털려도 서비스 DB는 열리지 않는다 |
| 원본 계정은 읽기 전용으로 둔다 | 배포 시스템이 털려도 저작 콘텐츠는 바뀌지 않는다 |

## 실무에서는

이전에 일한 교육 콘텐츠 회사에서는 **A 방식**이었다. 콘텐츠를 내보내는 시스템 하나가 모든 서비스 DB를 직접 알고 썼다.

- 상태를 바로바로 읽을 수 있다는 장점이 분명했다.
- 하지만 서비스마다 스키마를 따라가느라 손이 많이 갔다.
- 무엇보다 **한 번 뚫리면 모든 서비스 DB가 함께 뚫리는 구조**였다.

이 프로젝트는 그 경험을 바탕으로 B를 골랐다. "상태를 바로 읽는다"는 장점은 결과 메시지에 반영 내용을 담고 조회 계약을 두는 것으로 되살리고, 접속 정보가 한곳에 모이는 문제는 계약 뒤로 숨겨서 없앤다.

## 이행 계획

에이전트는 마지막에 **서비스 팀 소유의 별도 서비스**로 떼어 낸다. 이 프로젝트에서 실제로 그 단계까지 구현한다.

| 단계 | 모양 | 서비스 DB 접속 정보가 있는 곳 |
|---|---|---|
| 1. 지금 | 에이전트 하나(`data-migration-service`)가 모든 대상을 맡는다. 토픽 하나, 대상 목록도 에이전트에 있다. | 에이전트 한곳에 전부 |
| 2. 계약 분리 | 대상 목록을 배포 컨텍스트로 옮긴다. 계약(명령·결과·조회)을 정하고 결과에 반영 내용을 담는다. 대상 시스템마다 토픽을 나눈다. | 에이전트 한곳에 전부 |
| 3. 대상별 에이전트 | 에이전트를 대상 시스템마다 따로 띄운다. 계정 권한을 최소로 줄인다. | 대상마다 자기 에이전트에만 |
| 4. 떼어 내기 | 대상별 에이전트를 **각 서비스 팀 소유의 컨슈머 서비스**(예: 온라인캠퍼스 반영 서비스, 부트캠프 반영 서비스)로 옮긴다. 배포 시스템 코드는 고치지 않는다. | 각 서비스 팀 안에만 |

4단계가 끝났을 때 배포 시스템 쪽 변경이 **설정(토픽 구독자, 대상 목록)뿐**이면 이 결정이 맞았다고 본다. 배포 시스템 코드를 고쳐야 했다면 계약에 빠진 것이 있었다는 뜻이고, 그 내용을 이 ADR에 덧붙인다.

## 바꾸려면

**A로 되돌리기**: 대상 목록을 배포 시스템으로 옮긴 상태에서, 에이전트의 어댑터를 배포 시스템 안으로 들여 직접 호출한다. 계약 메시지 대신 메서드 호출이 된다. 보안 피해 범위가 다시 커진다는 점을 먼저 받아들여야 한다.

**C로 가기**: 4단계를 앞당기는 것과 같다. 서비스 팀이 계약을 구현하면 그 대상의 에이전트를 끈다.
